## v0.1 — localhost proof of concept

**Frozen:** `v0.1.0` · **May 2026**

### What we were trying to prove

The original brief was narrow on purpose: a digital-only, localhost-only web app that collects birth date, birth city, and lived cities, then renders twelve climate facts — a "kundli" — on the same page. No hardware, no print pipeline, no exhibition integrations yet.

Two constraints shaped everything:

1. Visitors could be born anywhere in the world.
2. Venue Wi‑Fi quality was unknown.

So the architecture had to be globally capable and cache-heavy.

### What we built

**Stack:** npm workspaces, Hono + SQLite server (`localhost:3001`), Vite + React web (`localhost:5173`), shared `data/` folder for bundled CSVs and cache.

**UI:** Single-page form. Birth date picker, birth city autocomplete (`CityCombobox`), repeatable stay rows with month-precision dates. Submit → twelve-cell grid on the same page. No routing, no wizard — everything visible at once.

<Figure
  src="/documentation/v0-1/form-and-grid.png"
  caption="v0.1 PoC — single-page form and live-generated 12-cell grid (Delhi 1993, with international stays). Captured from the archived build."
  wide
/>

**Data pipeline:**

```
Browser → POST /api/generate
  → geocode (SQLite cache → Open-Meteo Geocoding)
  → per-cell builders in parallel
      → weather (SQLite → Open-Meteo Historical ERA5, 1940→today)
      → climate projection (SQLite → Open-Meteo CMIP6, 2020→2050)
      → bundled CSVs (CO₂ ppm, national emissions, sea level)
  → 12 cells with source + confidence metadata
```

**Twelve cells:**

| # | Type | Source |
| --- | --- | --- |
| 1 | You (birth city + date) | Input |
| 2–3 | Birth year high/low temp | ERA5 via Open-Meteo |
| 4–5 | Latest birthday high/low | ERA5 |
| 6–7 | Summer/winter span across lived cities | ERA5 |
| 8 | National CO₂ emissions change | OWID CSV |
| 9 | Birth city rainfall change | ERA5 |
| 10 | Sea level rise | NOAA/CSIRO CSV |
| 11 | Atmospheric CO₂ ppm change | Mauna Loa CSV |
| 12 | Projected 2050 birthday temp | CMIP6 via Open-Meteo |

**Caching:** `better-sqlite3`, cache-first with live fetch on miss. Optional `prefetch` script could warm hundreds of cities ahead of time.

**Not built:** Deployment story, offline exhibit reliability, graceful degradation labels in the UI (backend had some confidence metadata but the frontend was thin).

### Why we scrapped it

v0.1 did its job — we validated the twelve-cell mapping and confirmed global coverage was feasible with Open-Meteo. But it was never venue-ready:

- Localhost-only, no production deploy path.
- Prefetch-heavy; uncached cities still hit live upstream APIs during the show.
- Single-page form felt like a developer tool, not an exhibition experience.
- No provenance surfaced to visitors; numbers appeared without context.

We archived it at `v0.1.0` and moved on. The code and a full build note live in `v0.1/docs/HOW-IT-WAS-BUILT.md` on `retired-0.1-0.2`.

## v0.2 — the precomputed climate database

**May 2026** · Retired before v0.3 started

### What we were trying to prove

If v0.1 was "call APIs at read time," v0.2 was "own the data plane." The bet: batch ingest once, serve from Postgres at exhibit time, never call upstream APIs from the kiosk.

**Stack:**

- **Ingest:** Python CLI (`klimate-ingest`) — Copernicus CDS / ERA5, IMD Pune gridded rainfall (1901–2024) and temperature (1951–2024), global indices (CO₂, sea level, emissions).
- **Storage:** Cloudflare R2 for raw artifacts, Supabase Postgres for places, grid mapping, `daily_weather`, rollups, provenance.
- **API:** Hono on `localhost:3002` — places search, annual/monthly/daily timeseries, bundled `POST /api/kundli`.
- **Web:** Vite + React + Tailwind + shadcn, parchment-ink almanac theme on `localhost:5174`.

### What we built

Phases 1–5, 4.5, and 6a shipped end-to-end:

1. Schema + place loader + CDS ingest scaffolding
2. R2 upload + hourly→daily transform + `daily_weather` upsert
3. Per-source aggregates (annual, monthly, seasonal)
4. Full API + bundled `/api/kundli` (all 12 cells)
4.5. Global indices (OWID, Mauna Loa, sea level) loaded into Postgres
5. Web UI — form, 3×4 kundli grid, provenance pills
6a. IMD gridded layer with per-variable source preference (`imd_temp` / `imd_rain` → ERA5 fallback)

**UI details worth keeping:**

- Parchment-ink visual language — felt like an almanac, not a dashboard.
- `PlaceCombobox` with cmdk + Radix popover for city search against the preloaded place table.
- `ProvenancePill` on every cell — source tier, quality score, date coverage.
- View-state machine: form → loading → result, with "Start over" returning to form.

**Data pipeline (read path):**

```
Browser → POST /api/kundli
  → resolve place slugs (delhi-in, mumbai-in, …)
  → query precomputed aggregates per cell
      → imd_temp / imd_rain for Indian cities where loaded
      → era5 fallback
      → global_indices for cells 8, 10, 11
  → 12 cells with status (ok / no_data / partial) + provenance
```

**Canonical test case** (verified in `v0.2/docs/STATE.md`):

Delhi born 1990-06-15, Mumbai 2014–2020, Bengaluru 2020→today. All 12 cells `ok`. Cells 2/3 from IMD temp (43.9°C / 3.7°C). Cell 9 from IMD rain (−7.4% over lifetime).

### What never shipped

- Phase 6b: IMD station / sub-station observations (blocked on IMDDS credentials).
- GHCN overlay, event snapshots.
- Production deploy beyond local Caddy routing.
- Automated tests.

### Why we scrapped it

v0.2 bought reproducible numbers and India-faithful IMD layers. It also bought:

- Supabase + R2 + Copernicus ingest time + Python tooling + cognitive load.
- A pipeline that was **partially incomplete** yet **fully operational** — meaning we were paying ops cost for marginal gain over what Open-Meteo already gives us for city-scale queries.
- Duplicate work that free, purpose-built APIs solve at exhibit QPS.

For a two-day, non-commercial, low-traffic installation, a thin orchestration layer with aggressive SQLite caching (v0.3's direction) was the better bet. v0.2 remains on `retired-0.1-0.2` as documented reference — schema, ingest CLI, API shapes, UI patterns we may borrow from.

## v0.3.1 — backend reboot + placeholder UI

**12–13 May 2026** · Commits on `main`

### What changed in thinking

After retiring v0.1 and v0.2, we cleared `main` and started fresh. The new prompt (`klimate-kundli-pipeline-prompt.md`) reframed the backend as a standalone Hono server:

- Open-Meteo + NASA POWER + Nominatim fallback chains
- SQLite cache (disk-backed, survives restart)
- Twelve-card `/kundli` endpoint with confidence labels
- No Supabase, no R2, no Python ingest at runtime
- 8-second global request budget, graceful partial responses

This was explicitly "backend first, UI later."

### What we built

**Backend (`src/`):**

- Hono app on port 8787
- Routes: `GET /health`, `GET /geocode`, `POST /kundli`, `GET /stats`
- Resolvers: geocoding chain, historical weather (ERA5 → NASA POWER → nearest pre-warmed city), CMIP6 projection, static CSV lookups
- Aggregations for all 12 cards
- `npm run prewarm` — warm cache for ~35 starter cities (expandable)
- `npm run fetch:static` — refresh bundled CSVs
- Vitest tests for cache, aggregations, resolver chains

**Open-Meteo paid tier:** Added `OPEN_METEO_API_KEY` support (Standard customer host) after hitting free-tier rate limits during prewarm. Later simplified routing when quota errors needed hardening.

**Web (`web/`):**

- Vite + React + shadcn scaffold
- `PageLayout` with max-width column

### Why the UI stayed dummy

We wanted the pipeline solid before designing the exhibit interaction. The twelve-card model from v0.1/v0.2 was still the backend contract, but product conversations were shifting toward a **monthly temperature comparison** narrative — childhood vs today — rather than a dense 3×4 grid.

## v0.3.2 — wizard + monthly delta chart

**23–24 May 2026** · Superseded by v0.3.3

### Product shift

Instead of twelve equal cells, the primary output became a single story: **how does the climate of your childhood compare to today?**

Inputs simplified:

- Birth **year** (not full date) + birth city
- Lived cities with year ranges on a horizontal timeline

Output: monthly temperature chart comparing a ±2-year window around birth against the most recent five complete years, plus derived insights and "remedies."

### What we built

**New backend route:** `POST /monthly-delta`

Accepts `birthCity`, `birthYear`, `livedCities[]`. Returns:

- Monthly mean temperatures for birth window and recent window
- Per-month deltas
- Hottest months in each window
- India national emissions change (birth year vs latest)
- Parents' generation comparison year (birth year − 25)
- City stint metadata for timeline rendering

Implementation in `src/routes/monthly-delta.ts` — sequential weather fetches per unique city stint, 45s budget, ERA5 via existing historical resolver.

## v0.3.3 — generational emissions rings + tooltips

**24 May 2026** · Superseded by v0.3.4

### Product addition

v0.3.3 extends the result view without changing wizard inputs. After the monthly temperature chart, **India national CO₂ emissions** now render as **two side-by-side tree-ring charts**:

1. **You** — rings from your birth year to the latest complete data year
2. **Your parents' generation** — same endpoint, starting at birth year − 25 (same offset as the temperature "parents' childhood" window elsewhere)

Both charts share one **absolute color scale** so the same Mt value maps to the same hue on either side. Ring **thickness** still encodes each year's share of that lifetime's total emissions — so a parent's chart has more rings (longer span) and the outer years dominate visually.

**Hover tooltips** on each ring show the calendar year and national CO₂ in Mt (OWID). Radial hit-testing keeps thin outer rings easy to target; the hovered ring stays full opacity while others dim.

### Backend

`POST /monthly-delta` response adds `parentsIndiaEmissions` — same shape as `indiaEmissions`, built with `buildIndiaEmissionsRings(statics, birthYear - 25, latestCompleteYear)` when the parents' birth year is ≥ 1940.

## v0.3.4 — exhibit deploy, hand fan, IMD peaks, visual polish

**May–June 2026** · Current work on `main`

### What changed in thinking

v0.3.3 made the result page feel complete for temperature + emissions. v0.3.4 is **venue-ready engineering**: ship the stack to a droplet + Vercel, add a second climate story (years you lived through that rank in each city's top-10 hottest since 1940), and tighten the wizard and typography so the kiosk reads as an almanac, not a dev tool.

### Production architecture

```
Visitor → klimate-kundli.vercel.app (Vite static UI)
              │
              └── VITE_API_URL → Cloudflare quick tunnel → trycloudflare.com
                        │
                        └── DigitalOcean droplet :8787 (systemd: klimate-kundli)
                                  ├── Hono API + SQLite cache (data/cache.sqlite)
                                  ├── optional IMD_API_KEY + IMD_EMAIL/PASSWORD (Indian peak °C on fan; JWT auto-refresh)
                                  └── Caddy optional for sslip.io / custom domain on :443
```

**Deploy artifacts:** `deploy/setup-droplet.sh`, `deploy/klimate-kundli.service`, `deploy/setup-cloudflare-tunnel.sh`, `deploy/cloudflared-quick.service`, `deploy/show-tunnel-url.sh`. Frontend env and tunnel drift troubleshooting: `docs/VERCEL_API.md`.

**Operational notes:**

- Tunnel hostname **changes** when `cloudflared-quick` restarts — update `VITE_API_URL` on Vercel and redeploy.
- `npm run build` emits `dist/index.js` for systemd; deploy skips Puppeteer on the server.
- Droplet public IP is whitelisted on the IMD portal for `IMD_API_KEY`; JWT from `POST /api/oauth/token.php` using portal login (`IMD_EMAIL` / `IMD_PASSWORD`), refreshed hourly — verify with `npm run imd:diagnose`.

### Product addition — record-hot years hand fan

After the monthly temperature chart and before emissions rings, the result view adds **"You've lived through N record-hot years"**:

- For each city stint, ERA5 annual means pick the **top 10 hottest years since 1940** at that grid point.
- Any calendar year you lived there that appears in that city's top 10 becomes a **fan blade** (one slat per year).
- Blade **height** encodes peak daily max that year; **color** encodes city; hover shows year, °C, date, rank, and source.
- **India:** when IMD station binding + cached peak exist, blade peak °C and tooltip use **IMD station** (`peakSource: imd_station`); qualification for "hot year" still uses ERA5 annual mean. Non-India and IMD misses stay on ERA5 with an explicit footnote.

**Backend:** `POST /monthly-delta` adds `hottestYears` — `buildHottestYearsInsight()` in `src/routes/monthly-delta.ts`, with `applyImdPeak()` via `ImdService`.

**Web:** `HandFanChart` (SVG fan, fixed blade capacity, global height scale), `HottestYearsSection` in `MonthlyDeltaChart`, copy in `RemediesSection` and `InsightsSection`.

### IMD layer (optional, droplet)

We revived a **thin IMD path** without v0.2's Postgres ingest:

| Piece | Location |
| --- | --- |
| Station map (~4511 stations) | `src/data/imd_station_map.json` via `npm run imd:build-station-map` |
| Nearest-station binding | `src/resolvers/imd/` |
| Peak cache | SQLite keys `imd:peak:v1:{stationId}:{year}` |
| Ops docs | `docs/IMD_SETUP.md`, `docs/IMD_IMPLEMENTATION.md` |

**Blocker for full historical fan:** many IMD HTTP endpoints are recent-only; long backfills may need one-time archive ingest into `data/imd/peaks/` (sketched in `IMD_IMPLEMENTATION.md`).

## v0.3.5 — life trails, public saves, frozen snapshots

**June 2026** · Current work on `main`

### What changed in thinking

v0.3.4 made the kiosk deployable and added the record-hot hand fan. v0.3.5 does two things: the result becomes more life-shaped, and every generated kundli becomes a durable public artifact. The live result can still render from JSON, but once the snapshot worker runs, shared links prefer frozen WebP chunks so later UI changes do not mutate past readings.

### Product additions

- **Lifetime temperature timeline:** `POST /monthly-delta` returns `tempTimeline`, a yearly mean-temperature series for lived-city stints from birth year through the latest complete year. It includes city order, warmest/coolest year, and lifetime temperature delta.
- **Life temperature chart:** `LifeTempChart` renders each lived year as a city-colored temperature dot with a vertical stem, hover details, source/confidence metadata, and headline copy keyed to warming/cooling delta.
- **Life rainfall orbit:** `LifeOrbitChart` wraps annual rainfall into a radial path from birth year clockwise to the latest complete year. Radius encodes annual rainfall, color encodes lived city, and hover shows year, city, and rainfall.
- **Public saved kundlis:** the home flow now generates monthly-delta data, saves the full input + result through `POST /kundlis`, stores the slug locally as "mine", then navigates to `/k/:slug`.
- **Explore gallery:** `/gallery` lists saved kundlis newest-first. Cards show birth city, birth year, created date, and whether the slug belongs to this browser.
- **Frozen snapshots:** `/k/:slug` shows a frozen snapshot frame when `snapshot.chunks` exists; otherwise it falls back to the live `MonthlyDeltaChart`. The capture-only route `/capture/k/:slug` renders the live result without the public page chrome so Puppeteer can freeze it.

### Data flow

```
Visitor
  -> /monthly-delta
  -> POST /kundlis
  -> /k/:slug
       -> snapshot chunks if frozen
       -> live MonthlyDeltaChart if not frozen yet

Snapshot worker
  -> /capture/k/:slug
  -> WebP chunks
  -> Supabase Storage bucket
  -> PUT /kundlis/:slug/snapshot
```

### Backend

`src/lib/temp-timeline.ts` adds `annualMeanTemps()` and `buildTempTimelineInsight()`. It groups daily `tmax`/`tmin` into annual means, clips each lived-city stint to birth year/latest complete year, and emits one chronological row per covered year.

`src/routes/monthly-delta.ts` includes `tempTimeline` in the `/monthly-delta` response next to rainfall, rain rings, emissions, global context, and hot-year fan data.

`src/routes/kundlis.ts` now supports the full saved-artifact lifecycle:

| Endpoint | Purpose |
| --- | --- |
| `POST /kundlis` | Save birth city, birth year, lived cities, and generated result; optionally trigger snapshot capture |
| `GET /kundlis` | List public saved kundlis for `/gallery` |
| `GET /kundlis/:slug` | Fetch saved input, result, and optional snapshot manifest |
| `PUT /kundlis/:slug/snapshot` | Store the frozen snapshot manifest, guarded by `KUNDLI_SNAPSHOT_TOKEN` in production |

`supabase/migrations/002_kundli_snapshots.sql` adds a nullable `snapshot` JSONB column to `kundlis` and creates the public `kundli-snapshots` storage bucket for WebP chunks.

Snapshot capture can be triggered by either:

- a generic webhook (`KUNDLI_SNAPSHOT_WEBHOOK_URL`, plus optional secret/auth header)
- GitHub `repository_dispatch` (`KUNDLI_SNAPSHOT_GITHUB_REPO` + `KUNDLI_SNAPSHOT_GITHUB_TOKEN`)

### Web

| Component | Change |
| --- | --- |
| `KundliApp` | Generates, saves, marks local slug, then redirects to `/k/:slug` |
| `KundliViewPage` | Shows frozen snapshot chunks when present, live chart while capture is pending |
| `KundliSnapshotFrame` | Displays the immutable WebP chunk stack with city/year header |
| `KundliCapturePage` | Minimal capture route with `data-kundli-capture-ready` marker |
| `GalleryPage` | Public listing of saved kundlis |
| `MonthlyDeltaChart` | Inserts life temperature chart and rainfall orbit after the monthly delta summary |
| `LifeTempChart` | New yearly mean-temperature trail with city legend and hover |
| `LifeOrbitChart` | New radial annual-rainfall chart using lived-city spans |
| `EmissionsRingsChart` | Clearer title, gradient legend, dynamic hub color, stronger growth-factor label |
| `MonthlyRainSection`, `RainRingsChart` | Shared data-source label formatting |

### Snapshot worker

`npm run capture:kundlis` runs `scripts/capture/kundli-snapshots.mjs`:

- accepts `--slug`, comma-separated slugs, `--all`, and `--force`
- waits for `/capture/k/:slug` to mark itself ready
- expands scroll containers so the full result can be chunked
- captures WebP chunks at configurable width, chunk height, viewport height, and device scale factor
- uploads to Supabase Storage when `SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY` are present, otherwise writes to `web/public/kundli-snapshots/`
- updates the saved record through `PUT /kundlis/:slug/snapshot`

`.github/workflows/kundli-snapshot.yml` runs the same script on GitHub Actions for `repository_dispatch` or manual `workflow_dispatch`.

- Rainfall orbit depends on `rainRings` data; if rain rings are unavailable, the orbit intentionally does not render.
- Snapshot capture depends on API + web app reachability from the runner (`KUNDLI_SNAPSHOT_WEB_URL`, `KUNDLI_SNAPSHOT_API_URL`) and Supabase service-role storage writes.
- Frozen snapshots are immutable by convention, not by bucket policy; `--force` intentionally overwrites a saved manifest for recapture.

## v0.3.6 — hot air balloons, lungs diamond, and Arctic ice lab

**June 2026** · Current work on `main`

### What changed in thinking

v0.3.5 added lifetime orbits, galleries, and snapshot rendering. v0.3.6 focus shifts to **refined visual metaphors and interactive sandboxing**:
1. Redesigning the lifetime temperature chart (formerly dots and lines) to use an evocative **hot air balloon metaphor**.
2. Redesigning the national emissions rings chart to use a centered **lungs-like diamond container with a rising matchstick smoke plume** representing Coal, Oil, Cement, Gas, and Flaring.
3. Adding a dedicated **Arctic Ice Lab sandbox** (`/ice-lab`) to test five different visual representations of sea ice decline (berg cross-section, floes nesting, flooded country outlines, lifetime ice-stripes, and dial gauge).
4. Substantially expanding the prewarm cache to **933 global cities** to ensure robust performance under poor venue network conditions.

### Product additions

- **Hot Air Balloon Temperature Trail:** In `LifeTempChart.tsx`, each lived year is rendered as a colored hot air balloon. Its vertical height encodes the annual mean temperature, and hovering displays specific peak temperatures, date of occurrence, and grid-point metadata.
- **Lungs Diamond Emissions Plume:** In `EmissionsRingsChart.tsx`, the original concentric circles are replaced by a stacked streamgraph centered along the vertical axis of a rotated diamond container. A matchstick sits at the base, and emissions are rendered as a rising smoke plume. The right side features an interactive storyline timeline allowing visitors to highlight individual years, view percentage contributions per fuel source, and compare their birth year baseline to today.
- **Arctic Sea Ice Sandbox:** A new route `/ice-lab` renders five distinct visualization concepts for representing the loss of Arctic summer sea ice (millions of km²) over a visitor's lifetime:
  - **Iceberg cross-section**: Faded/transparent iceberg cap representing ice volume lost since birth.
  - **Two floes nested**: A birth-year ice floe with a smaller today's floe nested inside, showing cracked gap losses.
  - **Your country drowned**: An outline of India filled with the equivalent area of lost ice.
  - **Lifetime ice-stripes**: One stripe per year (1979-now) where white indicates high ice extent and dark indicates low extent.
  - **Ice-lost dial**: A ring scaled to birth ice with the melted portion omitted as a missing sector.
- **Prewarm Batch and Ingest Expansion:** Scaled prewarming targets to `933` cities. Introduced `scripts/imd-ingest.py` for direct historical IMD station data ingestion.

## Architecture comparison

```
v0.1   Browser ──► Hono+SQLite ──► Open-Meteo (live + cache)
v0.2   Browser ──► Hono ──► Supabase ◄── Python ingest ◄── CDS/IMD/R2
v0.3   Browser ──► Hono+SQLite ──► Open-Meteo (live + cache)
                      │              └── optional IMD station peaks (IN fan blades)
                      └── POST /monthly-delta (primary UI path)

v0.3.4 Vercel UI ──tunnel──► droplet Hono (same as above)
v0.3.5 Vercel UI ──► droplet Hono ──► Supabase Postgres (saved kundlis)
                                      └── Supabase Storage (frozen WebP chunks)
                         GitHub Actions/Puppeteer ──► /capture/k/:slug ──► PUT snapshot manifest
v0.3.7 iPad Kiosk ──► /exhibition ──► /exhibition/k/:slug (distraction-free kiosk flow)
       Personal ──► / ──► /k/:slug & public pages (gallery, twin, etc.)
```

The through-line: **Open-Meteo keeps winning for city-scale exhibit queries.** v0.2's full Postgres ingest stayed retired; v0.3.4 adds a **minimal IMD sidecar** (station map JSON + peak cache + API on the droplet) for hotter, more credible Indian peak temperatures on the fan without reviving Python ingest at exhibit time. v0.3.5 uses Supabase narrowly: durable saved kundli JSON plus frozen snapshot assets, not climate computation.

## Capture pipeline

Screenshots and screen recordings regenerate via `scripts/capture/`. Static PNGs use Puppeteer `page.screenshot()`. Recordings use CDP `Page.startScreencast` → PNG sequence → ffmpeg, following the [screen capture pipeline write-up](https://www.arccc.co/words/screen-capture-pipeline/).

```bash
# from repo root — requires dev servers or archived branch worktrees running
npm run capture:docs -- --only v0-3-4   # latest embedded docs screenshots
npm run capture:docs -- --only v0-3-3   # three attendee profiles (emissions focus)
npm run capture:kundlis -- --slug abc123 --force
```

See `scripts/capture/README.md`. Documentation outputs land in `web/public/documentation/{version}/`. Kundli snapshot outputs upload to Supabase Storage when service-role env is present; otherwise they land in `web/public/kundli-snapshots/{slug}/`.
